# Scorbot state viewer

The viewer renders state; it is not a robot controller. Commands in a live scenario
go through `SimulatedPublisher`, the deterministic robot advances, and
`SimulatedRobotStateSource` converts its state to the common `RobotStateSnapshot`.
The viewer consumes only that snapshot.

## Install and launch

Install the optional dependency:

```console
uv sync --extra simulation --group dev
```

Open an interactive short scenario:

```console
uv run --extra simulation python -m src.simulation.viewer --two-robots
```

Bluey moves through homing, latency, left/right continuous commands, a speed change,
preemption, stop/settling, and a discrete target move. The second robot remains
independent and stationary. Close the PyBullet window or press Ctrl+C afterward.

PyBullet uses Maya-style camera controls: use **Alt/Ctrl + left drag** to orbit,
**Alt/Ctrl + middle drag** to pan, and the mouse wheel to zoom. Commander disables
the ExampleBrowser chrome because its labels render incorrectly on some Windows
display configurations, then draws its own persistent world grid and RGB axes.

After the scripted demonstration, the process enters live control mode. To skip the
demonstration and take control immediately:

```console
uv run --extra simulation python -m src.simulation.viewer --two-robots --no-demo
```

A separate **Commander Simulation Controls** window provides robot selection, Home,
Stop, presets 1/2/3, a speed slider, polar moves, Cartesian X/Y/Z moves, and live
returned state. Use `--no-control-panel` if keyboard-only control is preferred.

## Virtual and real command backends

The control layer targets the narrow `RobotCommandTarget` protocol, which is
implemented structurally by both `SimulatedPublisher` and Commander's network
`Publisher`. Each robot defaults to the `virtual` backend. A real Publisher must be
registered explicitly when launching:

```console
uv run --extra simulation python -m src.simulation.viewer --two-robots --no-demo --real-robot bluey=ROBOT_HOST:ROBOT_PORT
```

The Backend selector then offers `virtual` and `real` for Bluey. Switching to real
requires confirmation and stops the previous backend first. One robot can remain
virtual while the other uses a real Publisher. Closing the controls performs a
best-effort polar and Cartesian stop on every registered real Publisher.

Because the current physical protocol does not expose reliable pose telemetry, real
commands are mirrored into the local deterministic model for visualization and its
snapshots are labeled `command_estimate`. This is not actual robot position. A future
telemetry adapter can replace that estimate through the existing `RobotStateSource`
seam without changing the controls or renderer. Network stop is also not a substitute
for a physical emergency stop.

Robot controls:

- **Tab** selects Bluey or ER-V independently.
- Hold **A/D** to rotate the robot left/right.
- Hold **W/S** to extend/retract the arm. This sends Cartesian Y commands through
  the Publisher and uses the explicitly approximate IK mapping for visualization.
- **J/K** tilts the camera head up/down in 10-unit discrete steps.
- **H** homes, **Space/X** stops, and **+/-** changes speed.
- **1/2/3** sends one of three absolute simulated target poses.
- **P** prints command/state telemetry returned by both simulators.

These keys call each robot's `SimulatedPublisher`; they do not manipulate PyBullet
directly. Each simulated robot advances independently, returns a state snapshot, and
only then is rendered. The same list is always visible in the simulation control
window; keyboard commands are captured while the 3D PyBullet window has focus.

Cartesian buttons update the mock robot's X/Y/Z state in the ICD's tenths-of-a-
millimetre units. The visualization adapter uses PyBullet IK to display those values
as offsets from the legacy home endpoint. This mapping is marked `legacy
approximation`: its axis alignment and physical accuracy have not been calibrated.

The polar and Cartesian movement buttons use mouse press/release events: pressing a
button starts the corresponding continuous Publisher command and releasing it sends
the matching stop command.

The interactive viewer configures Cartesian speed at 1,000 logical units/second,
equivalent to 100 mm/second under the ICD convention. The reusable simulator keeps
its conservative default; this faster value is scoped to interactive visualization.

Record the exact snapshots generated by the scenario:

```console
uv run --extra simulation python -m src.simulation.viewer --record trajectory.jsonl --exit-on-complete
```

Replay those snapshots without rerunning commands or the simulator:

```console
uv run --extra simulation python -m src.simulation.viewer --replay trajectory.jsonl
```

Use `--headless --exit-on-complete` for deterministic non-GUI execution.

## State and provenance

`src.robot_state.RobotStateSnapshot` is deliberately transport-neutral. It carries:

- robot ID and timestamp;
- source type (`simulated`, `real`, `replay`, or `command_estimate`);
- movement state and logical pose/velocity when available;
- named joint positions/velocities when available;
- homed, command, and fault state when available;
- mapping quality (`physically_validated`, `legacy_approximation`, or `unknown`).

Unavailable fields remain `None`. A future real-robot adapter only needs to implement
the narrow `RobotStateSource.get_snapshot()` protocol. Real-time mirroring will not be
actual-state mirroring until the hardware supplies timestamps plus joint positions or
a physically validated pose, and preferably joint velocity, homed, command status,
and fault telemetry.

Multiple robot IDs are separate PyBullet bodies with independently configured base
positions and orientations. A future planned-versus-actual display can use separate
snapshot streams/bodies and label the planned one `command_estimate`; nothing in the
viewer currently promotes a commanded pose to actual telemetry.

## Kinematic truth and the legacy mapping

No physical mapping between `RobotPose` and the ER-4U URDF has been validated.
Cartesian X/Y/Z are ICD tenths of millimetres but remain logically independent in the
plant. The demonstration's opt-in adapter treats them as URDF-world X/Y/Z offsets and
uses inverse kinematics only to visualize the resulting endpoint. Discrete
azimuth/altitude units remain unspecified by the ICD.

For a useful demonstration, `LegacyPyBulletIKMapper` explicitly opts into the old
digital twin's assumptions plus an uncalibrated Cartesian visualization:

- logical azimuth maps linearly to `base_joint` at one degree per logical unit;
- logical altitude maps linearly to `pitch_joint` at one degree per logical unit;
- shoulder, elbow, pitch offset, roll, and gripper values use the old approximate
  home posture as the IK rest pose;
- logical Cartesian coordinates offset the home endpoint at 0.1 mm per unit before
  PyBullet solves the approximate joint pose.

Every resulting snapshot is labeled `legacy_approximation`, and the GUI displays that
label. This is a visual calibration, not a claim about encoder units, camera pose, or
the physical arm. A real calibration should replace it with a
`ConfigurableJointMapper` whose provenance is physically validated.

## Legacy reuse

The implementation reuses the existing ER-4U URDF, all eight STL meshes, the URDF
joint limits/velocities, and the approximate legacy home vector. It intentionally does
not reuse ActiveMQ, real-time GUI ownership, teleport-based command handling, or
hardcoded joint indices. Because the legacy URDF uses ROS `package://` mesh paths, the
loader creates a temporary path-resolved URDF at runtime while leaving the source
asset unchanged.

PyBullet mirrors each timestamped joint snapshot exactly with `resetJointState`.
Smoothness comes from the simulator's fixed-rate intermediate states; PyBullet does
not create a second motion timeline that could disagree with Commander.
